Status (13 Nov 2026): **PREPARED, NOT UPLOADED.** Both builds exist, are signed and have
been inspected; nothing has been sent to App Store Connect or Google Play, and nothing has
been pushed. Built from `f359132` on local `main` (tags `ios-v1.5.2-32` and
`android-v1.5.1-20`, local). What's New: [docs/releases/1.5.2/](../1.5.2/) (iOS, English and

**Do not push `main` or the tags until both stores have the builds.** This release exists
because the builds in the stores accept input they should not, and the diff says which.

## What is in it

The hardening pass, and nothing else: [docs/NEXT_RELEASE.md](../../NEXT_RELEASE.md) lists
every limit. In one paragraph:

- **iOS: a shared routine could crash-loop the app.** A routine code carrying an absurd
  kilogram target imported cleanly; once added on a phone with a max for that grip, the
  Today card trapped turning its percentage into an `Int`, at every launch, on every
  device the routine synced to. Kilogram targets are now clamped where a set is decoded
  (which heals a routine already saved), and every such conversion saturates.
- **Both platforms:** a routine code carries words rather than free text, with bounds on
  its size, nesting and name; a pasted AI reply has a length limit; the Motherboard
  decoder has the ceiling its siblings have, and every reading passes one plausibility
  check; the Frez request validates the serial, refuses redirects and reads a bounded
  answer; the CSV formula guard is complete and leaves numbers alone.
- **Android:** a routine link is read once; old export copies are purged; the clipboard
  is read as text.
- **watchOS:** the watch target ships a privacy manifest.
- The bundled licence notices are regenerated for this build.
- **No `Sources/Model` schema change**, so no CloudKit schema deploy is owed. The one
  file touched there (`WorkoutLog.swift`) changed a number conversion, not a field.
- The Frez access key is still compiled into both builds, as in 1.5.1 and 1.5.0. Taking
  it out is the relay, which is the release after this one (`docs/FREZ_RELAY.md` on the
  `frez-relay` branch).

## Verified

- `./build.sh test`: **1032 tests, 0 failures** on the bumped tree, 24 of them new
  (`Tests/SecurityHardeningTests.swift`).
- `UITests/ShareLinkImportUITests.swift`, which opens a routine code with a `1e30` kg
  target on a phone that has a max for that grip, adds it and checks Today: **passes**
  here and ends in "run.nuri.doigt crashed" on the 1.5.1 tag. That is the bug, reproduced
  and closed in the running app.
- Full UI suite on the iPhone 17 Pro simulator (iOS 26.5): 72 run, 59 passed, 8 skipped,
  **5 failures, none new, no crash.** They are the five the 1.5.1 record lists: `NightstandRunnerUITests` two,
  `RestFocusUITests` geometry, `RunnerActionMarginsUITests` French at the largest text,
  `KeyboardRoomUITests` at XXXL.
- The same suite on the iPhone Duo simulator, which `./build.sh uitest` now picks by
  default: 17 failures, none a crash, almost all "no tab bar found" from tests written
  for a phone whose tab bar is at the bottom. Three of the failing classes were run on
  the 1.5.1 tag on that simulator and fail the same five tests there, so they predate
  this release. The other twelve were not compared.
- Watch build and iOS Release build succeed.
- Android `:engine:test` **578** and `:app:testDebugUnitTest` **874**, 0 failures; the R8
  release build and the signed bundle build.
- `oracle` share (120 links), export, agent and runner all verify, so both engines still
  agree on every shared fixture, the 26 new ones included.
- The fuzz corpus that found the gaps (2,904 hostile routine links, 5,369 pasted texts,
  mutated frames for every gauge codec) runs clean through both engines.
